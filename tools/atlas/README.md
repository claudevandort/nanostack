# nanostack project atlas

A static-HTML, read-only view of the project state — services, ops, cross-service wiring, version trajectory, conformance counts, perf baseline.

The atlas is **derived** from the canonical docs (`docs/SUPPORT.md`, `docs/CHANGELOG.md`, `docs/PRD.md`, `docs/COVERAGE.md`, `docs/BENCH.md`, `CLAUDE.md`). There is no separate source of truth — if the atlas and the docs drift, rerun the builder.

## View it

```sh
# From the repo root:
python3 tools/atlas/serve.py
# Then open http://127.0.0.1:8765/   (or /plan.html for the plan board)
```

`serve.py` is a stdlib `http.server` variant that adds a single PUT endpoint (`/plan.overlay.json`) for the interactive plan board. For pure read-only use, `python3 -m http.server --directory tools/atlas 8765` also works.

`file://` doesn't — most browsers block `fetch('./data.json')` from a `file://` URL.

## Refresh it

```sh
python3 tools/atlas/build.py
```

This re-parses the canonical docs and rewrites `tools/atlas/data.json`. The HTML reads `data.json` on load — no build step, no bundler.

## What's on screen

- **Hero**: current version, the project tagline (extracted from `CLAUDE.md`), and headline tiles (service count, total ops, S3 Smithy coverage, test counts per SDK).
- **Service surface**: the four service columns (S3 / DynamoDB / SQS / SNS). Each op row is colored by its enforcement category (left border):
  - **enforced** — the row explicitly calls out request-time enforcement (e.g. policy eval).
  - **supported** — implemented and works against real SDK clients.
  - **accept-store-roundtrip** — accepted, stored, returned; not semantically enforced.
  - **partial / not supported / unknown** — should be self-explanatory.
  - Hover an op for the verbatim SUPPORT.md status; click the service header for the documented divergences.
- **Cross-service wiring**: SVG diagram of the five services + the flows between them. Solid lines for supported flows, dashed for not-yet-wired. Click a flow for the divergence notes.
- **Version trajectory**: pills for every release in `docs/PRD.md §15`. Shipped versions in green, planned versions dashed-amber. Click a pill for the release summary + conformance numbers after that release.
- **Performance baseline**: tiles from `docs/BENCH.md`'s "Current baseline" table.

## How the data flows

```
CLAUDE.md ──► tagline + version
docs/SUPPORT.md ─► services[*].ops, services[*].divergences, cross_service.flows, wedge
docs/CHANGELOG.md ─► test counts per version, release headlines
docs/PRD.md §15 ─► timeline entries (shipped/planned + scope + rationale)
docs/COVERAGE.md ─► S3 Smithy headline (covered / total)
docs/BENCH.md ─► perf baseline metrics
~/.claude/plans/<slug>.md ─► most-recent plan (active task plan)

→ tools/atlas/build.py
    → tools/atlas/data.json         (committed; atlas state)
    → tools/atlas/plan.json         (gitignored; private per-user plan)
        → tools/atlas/index.html     (atlas state via atlas.js)
        → tools/atlas/plan.html      (active plan via plan.js)
                ↓ (PUT via serve.py)
        ← tools/atlas/plan.overlay.json (gitignored; per-user annotations)
```

## Accessibility notes

- **No flashing or blinking** — transitions are capped at 150ms ease-out, no animations on load.
- **Theme toggle** (top-right) persists in `localStorage`. Auto-detects `prefers-color-scheme: dark`.
- **Keyboard**: `Esc` closes the side panel; focus rings on all interactive elements.
- **Search**: ops are text in the DOM, so `Cmd-F` / `Ctrl-F` finds any op name.


## Plan board (`plan.html`)

A read-only view of the *active task plan* — what the user has approved to build next.

```sh
python3 tools/atlas/build.py --plan-only   # refresh just the plan board
```

The builder reads the most-recently-modified `.md` file in `~/.claude/plans/` (overridable with `--plans-dir <path>` or `PLANS_DIR=...`), runs a generic H2-section parser with type-specific enrichers, and writes `tools/atlas/plan.json`. The page (`plan.html`) renders each section into a specialized card type:

- **Context / Approach** — paragraph prose.
- **Decisions Taken** — numbered card stack (one card per decision, paragraph-shaped decisions render with their breaks intact).
- **Scope** — horizontal phase rail; one card per `### Phase *` H3 sub-heading.
- **Critical Files** — 2-col split (Modified | New).
- **Open Items / Out of Scope** — small warning-tone "boundaries" cards.
- **Any other H2** — freeform prose card (fallback; plans never break the view).

The plan board navigates to/from the main atlas via the "Atlas | Plan" links at the top of both pages. Theme persists across the two.

**`plan.json` is gitignored.** Plans live in `~/.claude/plans/`, a per-user private directory; committing the parsed JSON would leak that into the public repo. If you clone the repo without a plan file, opening `plan.html` shows a friendly empty-state.

### Interactive annotations

Click any card on the plan board to attach a flag + free-text note:

- **Flags**: `—` (none) / `✓ agreed` / `? question` / `! blocked` / `🚫 out`. Each renders as a colored dot on the card after save.
- **Notes** are free text up to 800 chars. Inline markdown (`**bold**`, `` `code` ``, `[link](url)`) is honored when displayed.
- **Save** PUTs the full overlay to the server; **Cancel** discards. `Esc` closes the editor.

Annotations land in `tools/atlas/plan.overlay.json` (gitignored), which I (Claude) read on the next turn:

```json
{
  "annotations": {
    "decision-3-a5f9": {
      "flag": "question",
      "note": "Should this be configurable per topic?",
      "updated_at": "..."
    }
  },
  "plan_slug": "<slug>",
  "plan_mtime": "..."
}
```

Card IDs are `<kind>-<index>-<content-hash>` — stable across `--plan-only` rebuilds when the card content doesn't change. If the plan markdown changes (e.g. decision rewritten), the hash flips and the old annotation orphans (kept in the JSON, hidden in the UI).

**Writeable server required.** Plain `python3 -m http.server` doesn't handle PUT. Use `python3 tools/atlas/serve.py` (stdlib only, ~100 lines). It serves the same static files via GET and accepts PUT only on `/plan.overlay.json`. Bound to `127.0.0.1`.

## Roadmap

The MVP is read-only. Possible next steps:
- **Interactive plan board** — drag phases, toggle decisions, emit JSON patches that the parent agent reads on the next turn. Higher-bandwidth interface for the plan-mode workflow.
- **CI hook** that regenerates `data.json` on every merge to `main`. Plan files stay out of CI — they're per-user.
- **Op-detail drill-down extensions** — example AWS-vs-nanostack request/response diffs alongside the existing code-path links.
- **Print stylesheet** for static snapshots in PR comments.
